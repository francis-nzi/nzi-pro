# NZI Pro - Intelligent Dashboard: Codex Implementation Brief

## Context and Purpose

The current Dashboard is a **data display** tool. It shows what the numbers are but does not tell CRMs what to do about them. This brief transforms it into an **intelligence and action platform** - one that tells each CRM exactly which clients need attention today, surfaces risks before they become problems, and pre-briefs every client call with live data.

This is the single most important feature for enabling each CRM to manage 75-100 clients without sacrificing relationship quality.

**Tech stack (same as rest of app):**
- Backend: FastAPI, PostgreSQL via Supabase, psycopg driver, `%s` placeholders
- Frontend: Next.js 16, TypeScript, Recharts, Tailwind, shadcn/ui
- Auth: JWT Bearer tokens, org-scoped via `require_org(user)` from `services/tenancy.py`
- Database pattern: `with get_conn() as con:` (see `core/database.py`)
- Existing dashboard routes: `api/main_dashboard_routes.py`
- Existing dashboard component: `frontend/src/components/MainDashboard.tsx` (499 lines, 5 tabs)
- Existing client notes: `client_notes` table (`note_id`, `client_db_id`, `author`, `note_text`, `created_at`)

**Do not break any existing dashboard tabs or routes. All changes are additive.**

```sql
CREATE INDEX IF NOT EXISTS ix_client_touchpoints_client

  ON client_touchpoints (org_id, crm_owner, occurred_at DESC);
```

### 1.3 Create the `client_health_snapshots` table

Health scores are computed on demand and cached here. They are refreshed each time the intelligence endpoint is called.

```sql
CREATE TABLE IF NOT EXISTS client_health_snapshots (
  snapshot_id       INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  org_id            UUID NOT NULL,
  client_db_id      INTEGER NOT NULL,
  health_score      INTEGER NOT NULL DEFAULT 0,
  score_emissions   INTEGER,
  score_milestones  INTEGER,
  score_engagement  INTEGER,
  score_payments    INTEGER,
  risk_flags        TEXT,
  computed_at       TIMESTAMP DEFAULT NOW(),
  UNIQUE (org_id, client_db_id)
);
```

`risk_flags` is a comma-separated list of active flag codes (e.g. 'OVERDUE_CALL,EMISSIONS_OFF_TRACK').
`health_score` is 0-100. Use ON CONFLICT DO UPDATE when refreshing.

## TASK 2: Backend - Intelligence Endpoint

Create a new file `api/intelligence_routes.py`. Do not add these routes to `main_dashboard_routes.py`.

### 2.1 Health score calculation

The health score for a client is a weighted integer 0-100, computed from four components:

| Component | Weight | Source |
|---|---|---|
| Emissions progress | 30 pts | Most recent completed job: actual emissions vs target (net_zero_year / interim_year trajectory) |
| Milestone health | 25 pts | Current active job's milestone status (green=25, amber=15, red=5, none=10) |
| Engagement recency | 25 pts | Days since last touchpoint vs cadence threshold |
| Payment health | 20 pts | No overdue invoices=20, 1 overdue=10, 2+=0 |

**Engagement recency scoring:**
- Monthly cadence (threshold 35 days): <35 days = 25 pts, 35-60 days = 15 pts, >60 days = 0 pts
- Quarterly cadence (threshold 100 days): <100 days = 25 pts, 100-150 days = 15 pts, >150 days = 0 pts

**Emissions scoring:**
- Requires `benchmark_year` and at least one completed job with emissions data
- Calculate the expected linear reduction trajectory from `benchmark_year` to `net_zero_year`
- Compare the most recent completed job's emissions to the expected value for that year
- On track (<=5% above trajectory) = 30 pts; 5-15% above = 20 pts; 15-30% above = 10 pts; >30% above or no data = 5 pts

**Risk flags - append a flag code when:**
- `OVERDUE_CALL`: days since last touchpoint > cadence threshold
- `EMISSIONS_OFF_TRACK`: emissions >15% above trajectory
- `MILESTONE_RED`: active job has red milestone status
- `RENEWAL_90`: `engagement_end_date` is within 90 days
- `RENEWAL_30`: `engagement_end_date` is within 30 days
- `INVOICE_OVERDUE`: client has at least one overdue invoice
- `NO_ACTIVE_JOB`: client has no open or in-progress job this year

### 2.2 Action queue generation

An action is a dict with these fields:
```python
{
  "action_type": str,       # flag code, e.g. "OVERDUE_CALL"
  "priority": int,          # 1 (highest) to 5
  "client_db_id": int,
  "client_name": str,
  "crm_owner": str,
  "headline": str,          # e.g. "Call overdue by 12 days"
  "detail": str,            # e.g. "Last contact: 15 Jan. Cadence: monthly."
  "due_date": str | None,   # ISO date if applicable
}
```

Priority mapping:
- Priority 1: `RENEWAL_30`, `MILESTONE_RED`
- Priority 2: `INVOICE_OVERDUE`, `RENEWAL_90`
- Priority 3: `OVERDUE_CALL`
- Priority 4: `EMISSIONS_OFF_TRACK`
- Priority 5: `NO_ACTIVE_JOB`

Sort the action queue: priority ASC, then due_date ASC (nulls last).

### 2.3 Route definitions

```python
"""Intelligence routes - client health, action queue, call prep."""
from fastapi import APIRouter, Depends, Query
from api.auth import _current_user
from services.tenancy import require_org
from core.database import get_conn

router = APIRouter(prefix="/intelligence", tags=["intelligence"])
```

**`GET /intelligence/dashboard`**

Query params: `crm_owner: str | None` (filter to a single CRM; if omitted and user is not SuperAdmin, auto-filter to the logged-in user's CRM assignment label).

Returns:
```json
{
  "action_queue": [...],
  "portfolio_summary": {
    "total_clients": 0,
    "healthy": 0,
    "needs_attention": 0,
    "at_risk": 0,
    "avg_health_score": 0
  },
  "upcoming_touchpoints": [...],
  "renewal_pipeline": [...],
  "generated_at": "ISO timestamp"
}
```

`upcoming_touchpoints`: clients whose next touchpoint is due within 14 days, with `last_touchpoint_date`, `days_overdue`, `client_name`, `crm_owner`.

`renewal_pipeline`: clients with `engagement_end_date` within 90 days, with `engagement_end_date`, `days_remaining`, `health_score`, `client_name`.

This endpoint also refreshes `client_health_snapshots` using ON CONFLICT DO UPDATE for clients in scope before returning. Keep the refresh best-effort and bounded: use one batch upsert per client set, and if a full org-wide refresh would push the request past the latency target, refresh only the clients in scope for the current view and defer any broader backfill to a background process or the next request.

**`GET /intelligence/client/{client_db_id}/call-prep`**

Returns a call preparation brief for a single client:
```json
{
  "client_name": str,
  "crm_owner": str,
  "last_touchpoint": { "occurred_at": str, "summary": str, "outcome": str } | null,
  "days_since_contact": int | null,
  "health_score": int,
  "risk_flags": [str],
  "active_job": { "job_id": int, "title": str, "status": str, "milestone_status": str, "next_milestone": str, "days_to_milestone": int | null } | null,
  "emissions_summary": { "latest_year": int, "latest_tco2e": float, "yoy_change_pct": float | null, "vs_trajectory_pct": float | null } | null,
  "open_invoices": int,
  "overdue_invoices": int,
  "talking_points": [str],
  "engagement_end_date": str | null
}
```

`talking_points` is a list of plain-English strings generated from the data (not AI - derive them from the risk flags and data):
- If `OVERDUE_CALL`: `"Check in - last contact was {N} days ago"`
- If `EMISSIONS_OFF_TRACK`: `"Emissions {N}% above target trajectory - discuss reduction actions"`
- If `MILESTONE_RED`: `"Job milestone overdue - confirm data submission timeline"`
- If `RENEWAL_90`: `"Contract renewal due {date} - begin renewal conversation"`
- If `INVOICE_OVERDUE`: `"Outstanding invoice - confirm payment status"`
- Always append: `"Review progress against net zero target ({net_zero_year})"`

**`POST /intelligence/touchpoints`**

Log a new touchpoint. Body:
```json
{
  "client_db_id": int,
  "touchpoint_type": "call",
  "summary": "Q2 check-in call",
  "outcome": "positive",
  "next_action": "Send updated report",
  "next_action_due": "2026-07-01",
  "occurred_at": "2026-05-01T10:00:00"
}
```

Sets `org_id` from `require_org(user)`.

Sets `crm_owner` by reading `clients.crm_owner` for the given `client_db_id` at insert time - do **not** derive it from the authenticated user's display name. This ensures `crm_owner` on every touchpoint always matches the canonical assignment label on the client record and will join cleanly with the CRM Workload table. Use a subquery or a pre-fetch:

```sql
INSERT INTO client_touchpoints (org_id, client_db_id, crm_owner, touchpoint_type, summary, outcome, next_action, next_action_due, occurred_at, created_by)
SELECT %s, %s, crm_owner, %s, %s, %s, %s, %s, %s, %s
FROM clients
WHERE id = %s AND org_id = %s
```

Store the authenticated user's identity in `created_by` (the person who actually logged the touchpoint - may differ from the assigned CRM).

Returns the created touchpoint record.

**`GET /intelligence/touchpoints/{client_db_id}`**

Returns the last 20 touchpoints for a client, ordered by `occurred_at DESC`.

## Important Constraints for Codex

- **Do not modify or remove any existing dashboard tabs.** The Overview, Financial, Operations, Emissions, and Tasks tabs must continue to work unchanged.
- **Do not modify `main_dashboard_routes.py` except for Task 5.1** (adding two fields to the crm_workload array). All new routes go in `api/intelligence_routes.py`.
- **All new backend routes must use `require_org(user)` from `services/tenancy.py`** and scope every query with `org_id`.
- **Health scores are best-effort.** If a client is missing benchmark data, emissions data, or invoice data, compute the score from whatever is available rather than returning null or erroring. Log a warning but do not raise.
- **The `client_touchpoints` table is separate from `client_notes`.** Do not modify or replace the existing notes system. Touchpoints are structured interaction records; notes are freeform.
- **The intelligence endpoint must be fast.** Target under 800ms for the default CRM-scoped view. Use a single SQL query per data type where possible. The health score refresh should use INSERT ... ON CONFLICT DO UPDATE (upsert) in a single batch, not a loop of individual updates. If a superuser requests an org-wide view, keep the request bounded and fall back to partial refreshes or background backfill rather than letting the API hang.
- **Use `?` placeholders** (auto-converted by `core/database.py`) consistently with the rest of the codebase.
- **The `CallPrepPanel` and `LogTouchpointModal` must be reusable** - they will be invoked from at least two places (IntelligenceDashboard and the client detail page).
- **Do not use `localStorage`** for any state in the new components.
- **Recharts `ResponsiveContainer`** requires an explicit pixel-height parent div. Use `<div style={{ height: 240 }}>` wrappers wherever charts are used in the new components.
- **Follow the visual style of the existing dashboard:** use `Card`, `CardContent`, `CardHeader`, `CardTitle` from shadcn/ui; use the existing `ACCENT` colour constants from `MainDashboard.tsx`; use `Badge` for status indicators.
