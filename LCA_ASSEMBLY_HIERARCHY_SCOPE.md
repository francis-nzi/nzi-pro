# LCA Assembly Hierarchy — Scope

Date: 2026-07-25
Parent context: `sql_migrations/0058_lca_pcf_rebuild.sql`, `services/lca_engine.py`, `services/lca_bom_template.py`

## 1. Why this is being scoped

`sql_migrations/0058_lca_pcf_rebuild.sql` deliberately built `lca_line_items` as a flat list with no BOM tree, on the stated assumption that "real-world workbooks flatten multi-level BOMs for calculation purposes anyway."

A real BOM (P50-ECO, "P50 6LTR ECO - SCREEN") contradicts that assumption. It's a genuine multi-level assembly tree: raw materials roll up into named sub-assemblies (e.g. "P50 Inner Cylinder"), which are themselves referenced — by code, with a quantity — as ingredients of higher-level assemblies ("P50 Wound Inner Cylinder" → "Ready for screen" → "Printed"), four to five levels deep. Some sub-assemblies ("Syphon Tube Assembly", "Wound Inner Cylinder") are clearly meant to be reused across multiple products, not redefined per product.

The current schema cannot represent this. `lca_components` has no parent/child relationship, and `lca_line_items` links to at most one component with no "this line is itself an assembly" concept. Today's only workaround is manually pre-flattening the spreadsheet by hand before upload — which produces a correct carbon total but throws away the ability to define a sub-assembly once and reuse it, and loses traceability back to how the client's own BOM is actually structured.

## 2. What doesn't change

- `lca_assessments`, `lca_line_items`, `summarize_assessment()`, `compute_readiness()`, the BOM upload/template, the calc/hotspot/readiness UI — **all untouched**. This is additive, not a rebuild of what already works.
- A line item still ultimately resolves to a flat list of (module, quantity, unit, factor) before hitting `summarize_assessment` — that function's contract doesn't change at all.

## 3. Proposed design

### 3.1 Data model

Extend the existing `lca_components` library (client-scoped, mirrors `custom_factors`) with composite structure via a new join table — not a self-referencing column on `lca_components` itself, to avoid overloading `default_unit_mass`'s meaning (a composite's mass is *computed* from its children, not stored):

```sql
CREATE TABLE lca_component_children (
  child_link_id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  parent_component_id INTEGER NOT NULL REFERENCES lca_components(component_id) ON DELETE CASCADE,
  child_component_id INTEGER NOT NULL REFERENCES lca_components(component_id),
  quantity DOUBLE PRECISION NOT NULL DEFAULT 1,
  unit VARCHAR NOT NULL DEFAULT 'kg',
  sort_order INTEGER NOT NULL DEFAULT 0,
  notes TEXT,
  UNIQUE (parent_component_id, child_component_id)
);
```

A component with zero rows in `lca_component_children` is a **leaf** (today's behavior, unchanged — a real material with its own mass/origin/factor). A component with one or more children is a **composite/assembly** — the P50 example's "Syphon Tube Assembly" would be one row in `lca_components` plus two rows in `lca_component_children` pointing at the syphon tube and water filter leaf components, each with its own quantity.

`lca_line_items.component_id` already links a per-assessment BOM line to a library component — no change needed there. A line linking to a composite component means "this line is N units of this assembly," exactly matching how the real spreadsheet's reference rows work (row 20: "Wound Inner Cylinder, qty 1" as an ingredient line).

### 3.2 Calc engine — a new resolver step, not a rewrite

Add `services/lca_component_tree.py::resolve_effective_lines(lines, component_tree)`: walks each line item's `component_id`; if it points at a composite, recursively expands it into its leaf descendants, multiplying quantity down each level (mirrors exactly what a human would do multiplying through the spreadsheet's "Number" column by hand), and returns a flattened list shaped identically to what `summarize_assessment` already consumes. Leaf-only lines (100% of today's assessments) pass through unchanged.

`summarize_assessment(lines, ...)` in the calc/recalculate code path becomes `summarize_assessment(resolve_effective_lines(lines, ...), ...)` — one call-site change, function itself untouched.

**Cycle detection is mandatory, not optional**: a component that (directly or transitively) contains itself must be rejected at edit-time (when adding a child) and defensively guarded at resolve-time (raise/skip with a clear error rather than infinite-loop) — real BOM libraries with copy-pasted codes are exactly where this kind of accidental cycle happens.

### 3.3 UI — extend the existing Component Library panel, not a new area

`JobLca.tsx` already has an inline "library" modal (create/pick a component when adding a BOM line, backed by `GET/POST /clients/{id}/lca-components`) — this is where an assembly builder belongs, not a separate screen. Proposed: an "Assembly" toggle on the create/edit component form; when on, reveal a simple child-rows table (pick component from library + quantity + unit — the same picker UX already used for adding assessment line items) instead of the mass/origin/supplier fields. A composite component's card in the library list shows "Assembly (N parts)" instead of a mass, and its total mass in the picker is computed live from resolved children.

No changes proposed to the top-level BOM upload template/parsing — a client still uploads a flat sheet for whatever level they're building, and references a pre-defined assembly by its `component_code` exactly as they already reference any other component today.

## 4. Decisions needing your confirmation before I build this

1. **Live reference vs. snapshot for published assessments.** If "Syphon Tube Assembly" gets edited after 3 products' assessments already reference it, should those assessments' totals silently shift next time they're recalculated (live reference — corrections propagate automatically), or should an assessment's resolved values freeze once its `review_status` reaches `verified`/`published` (protects an already-signed-off ISO 14067 number from drifting without anyone re-reviewing it)? **My recommendation:** live reference while `draft`/`in_review`, frozen (resolved lines snapshotted, same pattern as the existing `lca_result_snapshots` table) once `verified`/`published` — but this is a real compliance-adjacent judgment call, not mine to make silently.
2. **Scope of reuse.** Mirror the existing component library's `client_db_id` (NULL = global/shared, else client-scoped) for assemblies too, so an assembly can be either client-specific or shared across all clients — same as leaf components today. Confirming this is the right default rather than something narrower (e.g. assembly reuse limited to one client only).
3. **V1 UI investment.** A flat child-rows table (simple, fast to build, consistent with the existing flat BOM table) vs. a fuller tree/drag-drop assembly builder. **My recommendation:** flat table for v1 — the real complexity here is the data model and calc engine, not the UI, and a flat table is enough to define even a 5-level-deep hierarchy (you just reference an assembly-as-child inside another assembly's own child list).
4. **Out of scope for v1, flag if you actually need it now:** auto-detecting nested structure directly from an uploaded flat spreadsheet (i.e. parsing bold/highlighted "assembly header" rows the way the source Excel visually marks them). This is real, ambiguous parsing logic with meaningful false-positive risk — v1 assumes assemblies are defined once in the library (by hand or a small dedicated import), then referenced by code in ordinary BOM uploads, not inferred automatically from arbitrary spreadsheet formatting.

## 5. Rough shape of the work

- Migration: 1 new table + cycle-safe insert/delete constraints.
- Backend: resolver module + cycle detection, `lca_components` CRUD extended for child rows, 1 call-site change in the recalculate path.
- Frontend: extend the existing library modal/form (assembly toggle + child-rows table + computed mass display).
- No changes to BOM upload, template, readiness scoring, module/hotspot breakdown, or reporting — they all consume the already-resolved flat line list exactly as today.

This is a genuine multi-file change (schema, calc engine, library CRUD, library UI) but stays additive throughout — nothing about today's flat-only assessments changes behavior once this ships.
